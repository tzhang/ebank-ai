## D4 · 基础设施选址:维持全海外,还是回国内云?

**为什么现在要定**:M1 就要选数据库(Neon/Supabase 海外区域 or 阿里云 RDS),M2 的 Agent 服务(RD-Agent 仅支持 Linux + Docker)也要落位。它同时约束 D1(微信登录需要已备案境内域名)与 D3(境内支付需要企业主体),所以排在最前。

> **建议**:M1–M2 维持全海外(Vercel 现状 + 海外 Linux 跑 Agent 服务);「回国内」写成带触发条件的迁移预案,本期不执行。

### 两条路线的真实代价

| 维度 | 全海外(现状) | 回国内云(阿里云 / 腾讯云) |
| --- | --- | --- |
| 上线周期 | ✅ 零备案,随时可上 | ⚠️ ICP 备案约 2–4 周 + 公安联网备案;域名与主体条件须先核实 |
| 域名 | ebank.ai 现状可用 | ⚠️ .ai 后缀大概率不在工信部备案白名单——回国内大概率需要新主域名,涉及换名与 SEO 迁移(以现行目录为准,待核实) |
| 访问体验 | 国内访问速度一般、偶发不稳定;对内容站 + CDN 可接受 | ✅ 国内访问快、稳定 |
| 合规负担 | 无备案义务;但面向国内用户的 UGC 平台责任仍在,访问有被屏蔽的不确定性 | UGC 论坛需落实后台实名、内容审核义务、日志留存;等保视规模另计 |
| 生态与支付 | GitHub/Vercel 生态、国际 API 直连;❌ 微信登录 / 微信支付、支付宝不可用(需境内主体+备案) | 微信生态、支付宝、短信签名等国内服务可接;DeepSeek 直连快 |
| 月成本(MVP) | ✅ Vercel 免费档 + Linux 2C4G 约 $10–20 + 托管 PG 免费档 | 主机与 RDS 相近,备案与合规的人力成本高一个量级 |

### 两件与选址无关的事,无论如何都要做

- **内容审核与举报机制(FRM-136)必须做扎实**——不管服务器在哪,平台对 UGC 的内容责任都存在;
- **架构上不绑定单一云**:数据层用标准 SQL + 对象存储、域名与 CDN 可切换、Agent 服务本就独立可搬。

### 什么情况下触发「回国内」迁移评审

1. 需要接微信登录 / 微信支付 / 支付宝等要求境内主体的功能(与 D1、D3 联动);
2. 国内可用性成为留存瓶颈(监控国内区域性能与失败率,数据说话);
3. 监管要求、资方要求或 UGC 风险事件暴露。

### 拍板后的第一动作

1. 数据库定档(建议 Neon 或 Supabase,海外区域),冻结 M1 数据层技术选型;
2. M2 Agent 服务测试机落位海外 Linux(2C4G 起步);
3. 备案观察项挂起,不投入。

**会上需确认**:是否存在已知的境内机构合作意向(银行/券商采购)会要求境内部署?若存在,D4 结论需反转。

## D1 · 登录方式:首版支持哪些登录通道?

**为什么现在要定**:认证是 M1 最前置模块,决定 AUTH-101~108 的范围与邮件服务选型。目标人群(银行/券商从业者、量化研究者、开发者、个人投资者)以国内为主,GitHub 覆盖率在开发者与量化人群中高、在银行从业者中低——邮箱是真正的兜底主通道。

> **建议**:首版做「邮箱密码 + GitHub OAuth」;微信扫码(P1)等 D4 备案主体就绪后推进;手机号(P2)暂缓。

### 三个通道的成本与约束

| 维度 | O1 邮箱 + GitHub(建议) | O2 微信扫码 | O3 手机号 + 短信 |
| --- | --- | --- | --- |
| 开发成本 | ✅ 约 3 人日 | 约 3 人日,但资质流程(主体 + 认证 + 备案域名)数周起步 | 约 2 人日,短信签名资质另计 |
| 资质要求 | ✅ 无特殊资质;GitHub OAuth App 免费 | ⚠️ 境内企业主体 + 微信开放平台认证(300 元/年)+ 已备案域名——与 D4 强耦合 | ⚠️ 短信签名审核普遍要求境内主体与备案应用 |
| 用户覆盖 | GitHub 覆盖开发者/量化人群(增长渠道),邮箱覆盖所有人(兜底) | ✅ 国内全人群,对银行从业者与普通投资者最友好 | 通用 |
| 合规与风控 | ✅ 邮箱不涉实名,负担最小 | 涉及个人信息共享,隐私政策需说明 | ⚠️ 手机号属个人信息(PIPL);接码平台刷号需风控 |
| 主要坑 | ⚠️ 国内邮箱(163/QQ)对境外发件方过滤——送达率需实测与调优 | 备案未解决前整个通道不可行 | 短信按条计费(约 ¥0.04–0.05/条),随量线性增长 |

### 需要写进验收的两点

- 微信开放平台「网站应用」登录在实践中普遍要求**已完成 ICP 备案的境内域名**——D4 维持海外期间,微信通道按不可行处理;
- 邮件服务:Resend / Mailgun 免费档(约 3k/月)足够 MVP;对国内邮箱需配好 SPF / DKIM / DMARC,**并把「30–50 封 163/QQ 投放测试」列为 M1 验收项**;不达标再评估国内邮件通道(同样依赖备案)。

### 什么情况下改变建议

1. M1 期间确认国内主体与备案可在 6 周内就绪,且微信是主要获客渠道 → 微信扫码提前到 M1;
2. 渠道确认目标用户几乎不用 GitHub 也不用邮箱(现实概率低)→ 以微信为主。

### 拍板后的第一动作

1. 注册 GitHub OAuth App(测试 / 生产两套 client);
2. 选定邮件服务、配置域名认证,验证 / 重置邮件模板文案过合规;
3. 确认 AUTH-107 / 108 移出 M1 范围(AUTH-106 防滥用保留)。

## D2 · 回测引擎路线:封装 RD-Agent、自研编排、还是自建轻量引擎?

**为什么现在要定**:它是 M2 的元决策,决定工期与长期架构。它不阻塞 M1——建议的落地方式是 **M1 第 2 周起跑一周技术验证(spike),会场上只认可路线与验收标准**。

> **建议**:以「封装 RD-Agent(方案 A)」为默认路线,以一周 spike 验收为门槛;不达标则按预案当场降级 B 或 C(免费档轻量回测始终可作产品分层保留)。

### 为什么不自研,核心有三条

1. **产品价值不在复造闭环。**我们要交付的是「中文、易懂、好看、普通人向」的工作坊 + 配额 / 任务系统 + 账号与社区——编排闭环对用户不可见。RD-Agent(Q) 已含因子 / 模型 / 联合进化三条闭环(NeurIPS 2025),WORK-220 未来直接延伸;
2. **LLM 生成代码的安全执行是自研最重的一块。**因子代码由 Agent 生成,必须在沙箱执行;RD-Agent 已内置 Docker 沙箱,自研 = 自己再解决一遍代码隔离;
3. **官方已默认 LiteLLM 后端并实验性支持 DeepSeek 官方 API**,与我们的模型策略一致,省去自建适配。

### 选 A 之前必须知道的三个「重」

- **它面向「自主长时研究」设计**,一个 loop 可能跑数小时——与产品「10 分钟内出首轮报告」冲突。对策(写进产品与封装层):任务异步化 + 完成通知(复用 FRM-134)、限制股票池(如仅指数成分)与区间、默认迭代 ≤3 轮、公共因子结果缓存;
- **仅支持 Linux + Docker**,Qlib 的 A 股数据需自备并持续更新(季频维护职责要接住);框架迭代快(0.8.0,2025-11),封装层必须薄——把 RD-Agent 当黑盒,只通过其入口触发、从输出落库,隔离升级冲击;
- **版本间行为可能变化**——这也是 spike 的第一验证对象。

### Spike:一周技术验证(建议 M1 第 2 周起,与 M1 并行)

- [ ] **S1** Linux + Docker 环境 pip 安装 rdagent 0.8.0,`rdagent health_check` 通过
- [ ] **S2** 按官方 DeepSeek 配置样例接通 LLM(LiteLLM + DeepSeek chat)+ embedding(SiliconFlow bge-m3),跑通 `fin_factor` 1–2 轮
- [ ] **S3** 记录单轮耗时(分钟)、token 与费用、产出因子 IC/ICIR 是否落在合理区间
- [ ] **S4** 验证能否「单步触发」——只跑一回合而非长时自治循环(决定 UI 的同步 / 异步策略)
- [ ] **S5** 探明输出结构(因子表达式、报告 JSON)能否被封装层稳定解析落库;server_ui / trace API 能否复用
- [ ] **S6** 测算 Qlib A 股数据落库的磁盘 / 更新 / 维护成本

### 验收标准与降级预案(会上确认后生效)

1. **达标**:单轮 ≤ 30 分钟、费用 < ¥2、可编程触发 → A 定稿为 M2 路线;
2. **时间不达标但功能成立**:通过限制股票池 / 区间、异步化收敛 → 仍走 A,调整产品侧预期;
3. **功能或费用失控**:当场评审转 B(自研编排,复用 Qlib 数据管线,约 +2–3 周)或 C(免费档轻量引擎 + A 留作付费档)。

### 拍板后的第一动作

1. 批准 1 周 spike 资源(工程师 1 名 + Linux 测试机 2C4G + DeepSeek / SiliconFlow Key);
2. spike 报告(对照 S1–S6 与验收标准)于 M1 中段回填本决策定稿;
3. M2 排期按 A 假定推进,封装层(factor-workshop-service)与 RD-Agent 解耦设计。

## D3 · 配额与商业模式:M2 用什么姿态上线?

**为什么现在要定方向**:WORK-208(配额与防滥用)在 M2 实现,额度参数现在就要给建议值;商业模式本身 M2 中期才生效——**这次只定方向与预算上限,不做付费体系**。

> **建议**:M2 以「免费配额 + 邀请制」上线;商业模式决策评审定在 M3 末(用因子广场数据说话);数据库预留 plan 字段即可,不建计费系统。

### 单次会话的单位成本粗估(DeepSeek 档,以官网现价校准)

| 成本项 | 量级(每会话,默认 ≤3 轮迭代) |
| --- | --- |
| LLM token | 每轮 3 个阶段约 2–6 万 tokens;单会话约 ¥1–3(DeepSeek 级定价;模型分级后取中下值) |
| 回测算力 | CPU 分钟级,单次回测 < ¥0.1(2C4G 包月约 $10–20 摊薄) |
| 合计 | **约 ¥1–3 / 完成会话**——免费档参数按此设计,spike 后用真实数字回填 |

### 建议额度参数(M2 默认,可调)

- 免费用户:每日 **2 个工作坊会话**(或 5 次回测,二选一为默认口径,会上确认);默认迭代 ≤3 轮,加轮消耗额度;
- 熔断:单用户每日成本上限 **¥5**,超限当日停发(NFR-306);
- 防刷门槛:邮箱验证 + 邀请码 + 异常模式检测(同 IP 高频);
- 邀请制同时服务冷启动(R4):首批 **100–500 个邀请码**发给内容作者与种子用户。

### 为什么现在不做积分墙和订阅

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| O1 免费配额 + 邀请制 | ✅ 采纳(建议) | 开发 0–2 人日(配额表即可);用户行为数据最干净,为 M3 末付费决策提供依据 |
| O2 积分墙 | ❌ P2,不做 | 与 PROF-113 积分体系合并;当前无内容与社区支撑,开发量收益不成比例 |
| O3 订阅制 | ❌ M3 末再议 | 境内支付需要主体 + 备案(D4 结论前不可行);无转化数据支撑定价;过早付费压制冷启动 |

### 什么情况提前开启付费评审

1. M2 内出现明显付费意愿信号(用户主动询问付费档、机构询单、邀请码供不应求)→ 提前到 M3 中段评审;
2. D4 反转(回国内)后支付通道可行,再评估订阅落地细节。

### 拍板后的第一动作

1. WORK-208 按建议参数设计(配额表 + 每日熔断 ¥5);
2. 用户表预留 plan / quota 字段,不建计费模块;
3. M3 末商业模式评审的数据埋点(M2 就要埋):会话完成率、因子 fork / 分享率、邀请码转化。
